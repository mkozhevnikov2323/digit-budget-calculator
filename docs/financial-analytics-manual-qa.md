# Ручная приёмка финансовой аналитики

Страница: `/analytics`, пункт меню **«Аналитика»**, заголовок **«Финансовая аналитика»**.

**Статус: ручная приёмка на реальных пользовательских данных НЕ ВЫПОЛНЕНА.**
Автоматические проверки используют только синтетические записи и подменённый транспорт.
Этот документ предназначен для самостоятельной проверки владельцем продукта в своём
локальном браузере. Успешные тесты и сборка не означают завершённую продуктовую приёмку.

Проверка строго на чтение: не создавайте, не редактируйте и не удаляйте реальные
операции ради теста. Не меняйте категории, займы, даты, настройки API или базы.
Если подходящих записей нет, отметьте сценарий «нет данных для проверки»;
ошибки и редкие случаи уже проверяются автоматически на синтетических данных.

## 1. Безопасная подготовка и доступ

- Используйте доверенную локальную копию приложения и уже согласованный локальный API.
  Самостоятельно убедитесь, что приложение обращается к ожидаемому окружению.
  Не переключайте его на production для выполнения чек-листа. Если безопасное
  окружение или источник данных нельзя подтвердить, остановитесь и отметьте `UNVERIFIED`.
- При уже установленных зависимостях frontend можно запустить локально командой
  `npm run dev -- --host 127.0.0.1` (Node.js 22). В ходе подготовки этого PR агент
  не запускает frontend/backend и не подключается к данным. Команда приведена для владельца.
  Установку или настройку отсутствующего окружения согласуйте отдельно.
- Войдите обычным способом в свою учётную запись. Не передавайте агенту пароль,
  токен или доступ к сеансу. Откройте «Аналитика», затем проверьте прямой переход
  на `/analytics` и обновление страницы: авторизованный пользователь остаётся на аналитике.
- В отдельном приватном окне без авторизации прямой переход на `/analytics`
  должен вести на публичную страницу без финансовых итогов.
- Не нажимайте кнопки добавления, изменения или удаления на соседних страницах.
  Аналитика использует существующие GET `/expenses` и GET `/incomes`.

## 2. Текущий и предыдущий месяцы

- Нажмите «Текущий месяц». Под селектором должны быть первое и последнее число
  текущего **UTC-месяца**, обе даты включительно, и пометка UTC.
  Около местной полуночи ориентируйтесь на текущую дату UTC, а не на дату устройства.
- «Предыдущий месяц» выбирает полный предыдущий месяц относительно текущей даты,
  а не относительно последнего выбранного периода. Для января это декабрь прошлого года.
- Для режима «Месяц» проверьте изменение месяца и года и кнопки
  «Предыдущий календарный период» / «Следующий календарный период».
  Годовой переход и число дней должны быть корректны, включая 29 февраля високосного года.
- При смене периода прежние итоги должны исчезать на время загрузки.

## 3. Квартал, год и произвольные даты

- Выберите «Квартал»: I — январь–март, II — апрель–июнь,
  III — июль–сентябрь, IV — октябрь–декабрь. Стрелки перемещают полный квартал.
- Выберите «Год»: ожидается 1 января–31 декабря; стрелки перемещают полный год.
- В режиме «Произвольный период» укажите безопасный небольшой диапазон,
  затем диапазон через границу года. Последний выбранный день включён целиком.
- Сделайте начальную дату позже конечной или очистите поле. Ожидаются понятная
  ошибка, отсутствие итогов и новых финансовых GET для невалидного периода.
  Введённые значения остаются в полях для исправления. Запросы, уже начатые
  для предыдущего корректного периода, могут завершаться — их результат не показывается.
- Исправьте даты: данные должны относиться только к исправленному диапазону.
  Если проверяете границы календаря 0001–9999, достаточно проверить поля и
  отключение недопустимых стрелок; не загружайте многотысячелетнюю историю.

## 4. Сверка с существующими списками за тот же UTC-интервал

Зафиксируйте даты аналитики локально. Для синтетического примера
`2024-12-31 — 2025-01-01` интервал равен
`2024-12-31T00:00:00.000Z ≤ date ≤ 2025-01-01T23:59:59.999Z`.
Следующая полночь уже исключена. Дата со смещением сравнивается как момент времени:
`2025-01-02T03:59:59.999+04:00` попадает в этот пример.

1. Откройте собственные списки «Доходы» и «Расходы» в отдельных вкладках.
   Сверяйте исходные операции, а не банковский баланс, график другой страницы
   или только сводную сумму месяца. Дождитесь завершения загрузки; желательно,
   чтобы другие сеансы в это время не меняли операции.
2. **Одинаковые подписи месяца ещё не гарантируют одинаковый интервал.**
   Списки фильтруют по `year/month`, backend строит их границы в часовом поясе
   сервера, а отображаемые даты и CSV используют локальный формат браузера.
   Аналитика передаёт явные UTC `startDate/endDate`. Часовой пояс реального
   запущенного API этим PR не установлен.
3. Если API использует UTC, для полного месяца выберите тот же месяц в обоих
   списках. Для квартала, года или custom-диапазона просмотрите все затронутые
   месяцы. Если сервер работает в другом известном часовом поясе, включите также
   месяцы, чьи серверные интервалы пересекают выбранные UTC-границы (в том числе
   соседние месяцы у границ). Не меняйте часовой пояс сервера ради проверки.
4. Просмотрите **все страницы пагинации** каждого такого списка. CSV-кнопки
   существующих таблиц выгружают текущую страницу, а не гарантированно весь период;
   выгрузка для этого чек-листа не требуется. `total` ответа — число документов,
   не денежная сумма. Не считайте одну операцию повторно при переходах по страницам.
5. Если нужна точная граница для записи, владелец может локально посмотреть
   исходное поле `date` в уже выполненном GET своей вкладки через Network браузера.
   Не создавайте ручных запросов, не копируйте токен, не сохраняйте HAR или полный
   ответ. Включайте запись только по её исходному моменту внутри UTC-интервала,
   а не по локализованному тексту даты. Дата только `YYYY-MM-DD` трактуется как UTC-полночь.
6. Посчитайте отдельно все доходные и расходные документы в интервале.
   Нулевая сумма — запись, которая увеличивает счётчик. Каждая строка документа
   учитывается один раз; аналитика не восстанавливает количество товаров.
   Для сумм используйте точную десятичную арифметику или целые копейки в доверенном
   локальном калькуляторе: синтетические `0,10 + 0,20 = 0,30 ₽`.
7. Сверьте поступления, расходы, оба счётчика и разность поступлений минус расходы.
   Разность может быть отрицательной. Если полноту списков, их часовой пояс или
   принадлежность записей интервалу нельзя подтвердить, отметьте сверку `UNVERIFIED`,
   а не «пройдено» или «ошибка аналитики». Два GET аналитики не являются атомарным снимком.

Реальные суммы и записи остаются только у владельца. Не переносите их в отчёт агенту.

## 5. Месячная динамика и пустые месяцы

- График называется «Месячная динамика расходов». Ключи — хронологические `YYYY-MM`.
  Сверьте суммы расходов каждого месяца; для custom-периода крайние месяцы
  содержат только записи внутри выбранных дней.
- При переходе через Новый год декабрь должен предшествовать январю следующего года.
  Месяцы без расходов присутствуют с нулём, а не пропускаются.
- В пределах одного месяца ожидается одна точка с видимым маркером.
  Даже короткий диапазон не превращает месячную сумму в дневные наблюдения.
- Если в вашей истории нет пустых месяцев или записей на границах, не создавайте
  их специально: отметьте отсутствие данных для ручной проверки.

## 6. Категории, суммы и доли

- Сверьте сумму каждой группы и количество расходных документов с тем же интервалом.
  В таблице должны быть все категории, даже если их больше 12. На графике допускаются
  12 крупнейших; при превышении лимита должна быть явная подпись об этом.
- Доля = сумма категории / все записанные расходы периода × 100%.
  Доли показаны максимум с двумя знаками; сумма отображаемых долей может немного
  отличаться от 100% из-за форматирования. При нулевой сумме расходов доли равны 0%.
- Отсутствующие/пустые метки объединяются в «Без категории», включая буквальную
  категорию с таким названием. Пробелы по краям названий убираются для группировки.
- Полное длинное название остаётся читаемым в таблице; на оси графика возможно
  сокращение. `constructor`, `__proto__` и Unicode должны отображаться как обычный текст.
- Подписи осей и подсказки — рубли, хотя расчётные значения внутри модели — копейки.

## 7. Займы и смысл итогов

- Расход с точной исходной категорией «Выдача займа» входит в записанные расходы;
  доход с точным источником «Возврат займа» — в записанные поступления.
  Эти суммы уже включены, повторно прибавлять их нельзя.
- Не пытайтесь сверять записанные движения с остатком непогашенных займов:
  это разные показатели. Отдельные подытоги займов модель вычисляет по точным меткам,
  но страница не показывает отдельные карточки этих подытогов.
- «Разность поступлений и расходов» не означает автоматически сбережения,
  свободные деньги, стоимость жизни, заработанный доход или остаток банковского счёта.
  Нормализация займов, переводов и возвратов в этой версии не выполняется.

## 8. Исторические суммы с неподдерживаемой точностью

- Синтетический пример неподдерживаемой суммы — `1.005 RUB`: автоматического
  округления до копеек нет. Ожидается сообщение о неподдерживаемой точности и
  «Итоги периода не рассчитаны» вместо частичного или нулевого результата.
- При отрицательной, нечисловой, небезопасно большой сумме или переполнении
  также должна показываться ошибка. Реальные нулевые значения и `0,01 ₽` допустимы.
- Backend хранит Number и не гарантирует максимум два десятичных знака:
  историческая запись может пройти серверную валидацию, но остановить аналитику.
  Не исправляйте и не создавайте реальные записи для воспроизведения. Сообщите
  только класс ошибки; отдельное решение по обработке истории требует согласования.

## 9. Загрузка, ошибки и пустой период

- На загрузке или refetch видны индикатор и текст, финансовые итоги скрыты.
  При нескольких быстрых переключениях итог должен соответствовать последнему
  выбранному периоду, даже если старый запрос завершится позже.
- «За выбранный период операций нет» и нулевые итоги допустимы только после
  успешного полного ответа по обоим видам операций. Нулевые операции увеличивают
  счётчики и не должны превращаться в сообщение об отсутствии записей.
- Ошибка сети/API, отсутствующий ответ, неверная дата/ID, дубликаты или неподтверждённая
  полнота списка должны давать ошибку без финансовых итогов.
  Для `noPagination=true` ожидается `page: 1`, `total = limit = длина массива`;
  для пустого ответа длина, `total` и `limit` равны 0.
- Не провоцируйте неполный ответ изменением API, БД или реальных записей.
  Необязательную проверку сетевой ошибки можно выполнить через Offline в DevTools
  и обновление страницы, затем вернуть Online и обновить снова. Ничего не отправляйте
  из форм. Состояние сетевого сбоя может выглядеть иначе при действующем service worker
  или кэше — фиксируйте наблюдение без вывода об исправности расчёта.

## 10. Мобильный и настольный интерфейс

- Проверьте ширину около 320–375 px и 1200 px, портретную ориентацию и увеличение текста.
  Графики не должны вызывать горизонтальную прокрутку всей страницы; таблица
  доступна независимо от графика, суммы и длинные категории читаемы.
- Заголовок страницы, секции категорий/динамики, названия полей и подсказка UTC
  должны быть доступны. Проверьте Tab, Shift+Tab, Enter, стрелки в селекторах
  и заметный фокус без мыши.
- Ошибка объявляется как alert, загрузка — как status с доступным индикатором.
  Автотесты JSDOM с заданной шириной не заменяют визуальную проверку браузером.

## 11. Безопасный отчёт о проблеме

Записывайте результаты локально: «пройдено», «ошибка», «нет данных для проверки»
или `UNVERIFIED`. В issue/чат передавайте только обезличенное описание:

```text
Версия frontend: <commit>
Версия локального API: <commit, если известен>
Браузер / ширина: <без личных данных>
Сценарий: custom-период через Новый год
Шаги: <действия с фильтрами>
Ожидание: <правило, без реальных сумм>
Наблюдение: <текст класса ошибки или безопасное описание>
Воспроизведение на синтетике: <выдуманные даты/суммы, либо пока не воспроизведено>
Статус: <ошибка / UNVERIFIED>
```

Не вставляйте в ChatGPT/Codex реальные операции, их ID, суммы, категории с личными
сведениями, комментарии, получателей, полные API payload, токены, заголовки
авторизации, cookies, пароли или строки подключения. Не отправляйте HAR и
необработанные снимки экрана. Если нужен скриншот, сначала замените чувствительные
данные и закройте панели Network/Storage. При подозрении на неверные итоги
приостановите доверие к отчёту; агенту достаточно обезличенного сценария.

## 12. Что остаётся предварительным

- UTC — временное соглашение, постоянный отчётный часовой пояс не утверждён.
- Формулы отражают записанные движения. Требуют продуктового решения нормализация
  займов, переводов, возвратов, начальных остатков и покрытие банковских счетов.
- Политика исправления неподдерживаемых исторических сумм отдельно не утверждена;
  текущая версия сообщает ошибку и ничего не округляет/не сохраняет.
- Два GET не дают атомарного снимка; метаданные не доказывают отсутствие систематических
  пропусков сервером. `noPagination` может быть дорогим на большой истории.
- Совместимость подтверждена чтением исходников backend на коммите
  `b6cafc9559608ec0592b64bcd11bc10eb17dab8a`, а не обращением к работающему сервису.
  Версия и часовой пояс фактически используемого API требуют подтверждения владельцем.
- Эта работа готовит первую приёмку, но не подтверждает её прохождение на реальных данных.
