# RFC F1 — Серверный анализ регулярности и классификация финансовых операций

**Статус:** PROPOSAL — документ для архитектурного и продуктового согласования; не разрешает реализацию API, схему БД или миграцию.  
**Проект:** Budget Calculator, два самостоятельных репозитория: frontend `mkozhevnikov2323/digit-budget-calculator` и backend `mkozhevnikov2323/digit-budget-calculator-api`.  
**Срез кодовой базы:** frontend main `df1eaa37d448247d12e18065e6a52ae1ae5727b5`; backend main `47a428c06ba665b784fdda3dd0edc1b29da8413a`.  
**Продуктовое решение владельца:** комбинированный анализ по категориям и похожим операциям; возможность ручной переклассификации; аналитика по периодам.  
**Связанные документы:** `docs/financial-planning-phase2-rfc.md`, `docs/financial-classification-owner-review-rfc.md`, `docs/financial-analytics-reporting-policy-rfc.md`.

## 1. Цель и нецели

Цель — предоставить понятную статистику доходов и расходов за месяц, квартал, год и выбранный диапазон с прозрачными автоматическими рекомендациями по повторяемости. Отдельно учитывать ручные решения пользователя. Исходные операции, их суммы и текущие HTTP-контракты не должны молча меняться.

Нецели этого RFC/PR: реализовать классификатор, запустить миграцию, сохранить решения, изменить финансовые записи, интегрировать OCR/AI, подключить платный сервис, строить бюджетные резервы или изменять существующие отчёты. Никаких production-файлов не меняем.

**Важно:** периодичность — наблюдение, а не доказанная экономическая роль. Регулярный банковский перевод или выдача займа не становится «повседневным расходом» от частоты. Редкая покупка не автоматически «крупная цель», «чрезвычайный резерв» или «долгосрочный капитал».

## 3. Разделение ответственности

**Backend (источник истины):**
- owner-scoped чтение и валидация исторических операций;
- вычисление регулярности категорий и похожих платежей;
- генерация версионированных, объяснимых автоматических рекомендаций;
- согласование ручных решений и правил при появлении одобренного persistence;
- агрегированная аналитика по периодам, без двойного учёта;
- контроль прав, согласованности, ограничений объёма, конкурентных записей.

**Frontend (presentation/client):**
- выбор периода, визуализация графиков, таблиц и evidences;
- отображение различий между «автоматически предложено», «подтверждено вручную», «не определено»;
- явный выбор/сброс/подтверждение, сообщения об ошибках и stale;
- RTK Query/verified session boundary, сброс кэша при смене credentials;
- временные локальные draft только в пределах явно обозначенного session lifecycle.

Не поддерживать два независимых «авторитетных» движка рекомендаций в frontend и backend. Существующий frontend resolver/reviewSession сохраняется для локального UX и проверки согласованности данных, но не становится второй серверной политикой. Отдельный общий пакет типов возможен позже, только по согласованию.

## 4. Двухуровневая группировка

### 4.1 Category/source recurrence

Расходы: ключ (подтверждённый владелец, dataset=expenses, достоверная идентичность категории); доходы: (владелец, dataset=incomes, source). Если доступны только текстовые названия, маркировать происхождение как label-only и не утверждать совпадение system/custom ID. «Без категории» не создаёт ложный единый значимый кластер. Доходы и расходы никогда не смешиваются.

### 4.2 Similar-operation recurrence

Для расходов предлагаемый строгий составной ключ (владелец, dataset, идентичность категории при доступности, title, recipient). Текстовая нормализация v1 — trim, сжатие серий пробелов, согласованный case-folding, без fuzzy/семантической догадки. Точная политика Unicode/локали и пустых/различающихся полей остаётся OPEN. Размер платежа — признак вариативности, а не обязательное равенство: рост аренды не разрушает серию.

Для доходов схема не содержит title/recipient; похожесть пока ограничена source. Не говорить пользователю «один и тот же плательщик», если известен только источник.

Уровни независимы. Пример: «Продукты» ежемесячны, но «Ноутбук» в одной категории электроники может встретиться только однажды. Если частоты группы/категории расходятся, вернуть обе оценки и причину, а не склеивать в один «достоверный» результат. Для получения title/recipient после существующей Phase 1 validation нужен отдельный checked recurrence adapter; не передавать raw Mongo/REST payload в чистый алгоритм.

## 5. Время, полнота и look-ahead

Предложение v1: rolling **12 завершённых UTC-месяцев**, непосредственно предшествующих месяцу оцениваемой операции. Окно не включает её текущий незавершённый месяц и будущие записи. Для исторического отчёта вычислять результат **as-of каждого месяца**; не использовать информацию, которая ещё не существовала к моменту этого месяца.

Для категории и похожей группы считать:
- count всех событий; count distinct active month keys (несколько чеков за один месяц считаются одним активным месяцем);
- covered month count и source completeness;
- последовательность активных месяцев, пропуски, интервалы;
- недавнюю серию, возраст наблюдения, недостаток информации;
- стабильность признаков/сумм лишь как вспомогательные evidence.

Отсутствие записи в **полном подтверждённом** месяце — значимое наблюдение; отсутствие данных, неполный page, ошибка сервера, разрыв покрытия или неизвестная длительность истории — не нулевое число операций.

Пример **кандидатных** порогов при 12 полноценных месяцах, не APPROVED:
- 9–12 активных месяцев: regular;
- 3–8: periodic;
- 1–2: observed_rare;
- отдельный emerging_pattern для новой серии 3+ последовательных месяцев при коротком жизненном цикле;
- insufficient_history / ambiguous при неполноте или конфликте.

Ежегодная периодичность по одному наблюдению за год не подтверждается; нужна история 24–36 месяцев и отдельный алгоритм. Классификатор должен сохранять evidence и policyVersion. Никакой confidence в процентах без валидации качества; сначала дискретные факты и причины.

Отдельный OPEN: отчёты за давние годы могут потребовать историю раньше выбранного периода. Нужны измерения и лимиты; запросы и расчёты не должны неопределённо читать всю БД.

## 6. Роль, слой, автоматический вывод

Существующие коды (provisional): роли ordinary_expense, ordinary_income, loan_issuance, loan_repayment, refund, internal_transfer, capital_movement и др.; spending layers everyday, irregular, emergency, major_goals, long_term_capital.

Алгоритм **может** предлагать spending layer everyday для повторяющегося **уже надёжно установленного ordinary_expense**, irregular для подтверждённого периодического ordinary_expense; окончательное сопоставление и пороги — OPEN. Регулярность **никогда сама не устанавливает economicRole=ordinary_expense**, не назначает слои обычному доходу, возврату займа, перемещению капитала/межсчётному переводу. Rare/insufficient не превращается автоматически в major_goals/emergency/long_term_capital.

Нужны явно различимые статусы:
- observed recurrence (измерение);
- suggested assignment (автоматическое, **не подтверждено**);
- manually reviewed/approved;
- explicit_unclassified;
- error/stale/insufficient history.

Предварительные суммы можно показывать в отдельных аналитических срезах только с маркировкой. Не смешивать их с подтверждённой стоимостью жизни или гарантированными накоплениями.

## 7. Правила и ручная корректировка

Кандидатный порядок приоритета:
1. явное ручное решение по exact (owner, dataset, operationId + проверенная актуальность);
2. отдельно утверждённое пользователем правило по группе;
3. автоматическая рекомендация;
4. не определено.

Не запускать массовое применение к похожим операциям без явного согласия, количества затронутых строк и просмотра примеров. Приоритет решения должен быть объясним: ручное исправление не удаляет автоматические evidence и не изменяет исходную запись.

**Долговременное хранение не одобрено этим RFC.** Предпочтительная альтернатива — отдельные owner-scoped records ручных решений и правил, с source dataset+ID, версией таксономии/алгоритма, evidence provenance, revision/concurrency token, timestamps и audit. Схему коллекции/индексов/retention/миграцию проектировать и утверждать отдельно. Запрещено дописывать скрытые новые поля в expense/income или сохранять всё в localStorage.

Без authoritative expected revision (сейчас frontend caller_local не серверный CAS) нельзя обещать безопасное overwrite при параллельном изменении финансовой операции. Предложить read/precondition/409 policy и проверить eventual consistency до write API.

## 8. Предварительные HTTP-контракты (НЕ утверждены)

Кандидаты для отдельного контрактного review:
- read recurrence/analytic report с period, policyVersion, classification status и evidence;
- read operation classifications с полными dataset+ID и owner scope, видимым только на сервере;
- write/manual override и reset с явно разрешённой идентичностью dataset+ID, expected revision и идемпотентностью;
- управляемые user-approved rules — отдельный этап.

Примеры имён маршрутов: GET /analytics/recurrence, GET /analytics/classification, PUT/DELETE /classifications/:dataset/:id. Это **не требование добавить именно эти endpoint**. Первично определить форму ответа и совместимость с имеющимся GET /expenses, GET /incomes, GET /balance. Не менять их ответы ради нового сервиса без отдельного согласия.

Ответ должен раскрывать policyVersion, asOf/coverage, status, evidence, provisional taxonomy, confirmed-vs-proposed source, partial/error state и готовые агрегаты в точных денежных единицах. Нельзя отправлять payload другого владельца, в том числе при кешировании.

## 9. Безопасность и достоверность

- Backend устанавливает владельца из JWT / auth middleware; owner из body/query игнорируется как полномочие.
- GET и особенно PUT/DELETE должны проверять принадлежность исходной операции.
- Тесты: no token, invalid token, wrong owner, A/B same operation ID patterns, late responses, same-owner new-session and A/B/A.
- Исторические чтения: проверить полноту, sorting, UTC границы [startInclusive,endExclusive), count metadata, ограничение page/size, частичное падение datasets.
- У текущих GET при startDate/endDate используются Date(string), $gte/$lte; нужно отдельное contract test на последний день/таймзону прежде чем считать эти GET достаточными.
- Original money хранится в Number; backend-аналитика должна иметь явный безопасный контракт конвертации в целые копейки, ошибки неподдерживаемой точности/overflow, без незаметного округления и double count.
- Загрузку финансовой истории не логировать; не использовать реальные записи в тестах, сторонние AI/облака или персональные данные в error messages.
- Смена токена, пользовательская сессия, refetch и устаревшие рекомендации должны быть fail-closed.
- Без серверных auth/owner contract tests на изолированных тестовых данных не открывать live manual-classification UI.

## 10. Performance и lifecycle

Перед backend API:
- измерить на синтетике типичное и стрессовое количество операций за 12/24 месяца;
- определить строгие лимиты истории (время, count, payload) и стратегию отказа/пагинации;
- выбрать однопроходную/индексируемую группировку O(N)–O(N log N), а не отдельный годовой запрос для каждой строки;
- обеспечить защиту от stampede, race/refetch, исключение неполных результатов;
- оценить нужные MongoDB индексы owner+date, **не создавать/менять индекс без отдельного согласования**;
- сначала вычисление на запрос / доказуемый cache; не записывать автоназначения в каждую transaction;
- при добавлении/изменении/удалении операции корректно инвалидировать соответствующие сводки, не обещать realtime без механизма.

История со старой датой может изменить рекомендации после себя. Нужны договорённости о «as-of» и версиях рекомендаций прежде чем выпускать API.

## 11. План небольших PR, зависимости и откаты

**F1 (этот PR):** только межсервисный RFC; без source/test/schema/API, PR остаётся для review.

**Backend B2:** подготовить app/server separation и TS development execution с минимальными smoke-тестами, сохранив CommonJS и поведение локального запуска; два малых PR при необходимости, без изменения API/БД.

**Backend B3–B9:** поэтапно типизировать существующие модули, добавляя направленные проверки; согласованная миграция без общего rewrite. Часть независимой pure recurrence логики можно проектировать после подходящих TS foundations, но нельзя обходить security- и data-contract gates.

**Backend contract/security gate:** синтетическая MongoDB/test DB, реальные middleware, owner filters, auth, date boundaries, полной истории и money precision; без production DB. Требуется до live read/write integration.

**Recurrence engine PR:** чистый TypeScript в backend, synthetic fixtures, deterministic grouping, UTC history, insufficient cases; без endpoints и записи в БД.

**Read API PR:** ограниченное owner-scoped чтение/валидация полной истории, вычисление recommendation/evidence, verifiable totals, versioned DTOs; без mutations.

**Frontend analytics PR:** подключить read-only recommendations в существующий /analytics и таблицы; показывать автоматические/ручные/unknown отдельно, не менять исходные totals. Reuse UI PR #22 after review; он ещё открыт.

**Persistence design RFC + migration approval:** отдельно одобрить Mongo collection, индексы, concurrency, audit/retention. Пока нет согласования — только временные решения в памяти, явно обозначенные как временные.

**Manual write API PR:** owner-isolated mutations, expected revision, idempotency, audit и тесты; только после утверждения схемы.

**Frontend manual integration PR:** RTK Query mutations с unwrap, ошибки не закрывают UI и не теряют введённое, revalidation, sync по сессии; ручное исправление всегда имеет приоритет.

**Rollbacks:** чистый engine откатывается отключением потребителя; read API — маршрутом/feature switch без миграции; persistence требует отдельно документированный safe rollback, без потери manual decisions. Backend TypeScript миграцию не смешивать с изменениями финансовой логики.

## 12. Матрица тестов для будущих implementation PR

1. Покупки 15 раз за месяц = один active month; 12 месяцев = регулярная категория.
2. Категория регулярна, конкретная покупка единичная: разные результаты.
3. Аренда меняет сумму, но сохраняет title/recipient; серия не пропадает.
4. Одинаковое title у разных категорий и owners; нет склейки.
5. system/custom same label без достоверного FK → ambiguous, не false ID.
6. 3 недавних месяца последовательны; 3 разбросанных месяца — разные evidence.
7. Разовая страховка за год не объявляется гарантированно ежегодной.
8. Декабрь/январь, високосный февраль, UTC boundaries и последний день периода.
9. Отсутствующий месяц против отсутствующего ответа API.
10. Доходы/source vs расходы/category, отказ от inappropriate spending layer.
11. Регулярная выдача займа / внутренний перевод: не ordinary expense.
12. Неверная сумма, >2 знаков, overflow, плохие даты/ID → явная ошибка без частичного итога.
13. Перестановка входного массива → тот же результат и те же причины.
14. Изменение суммы/даты старой записи → только допустимые после неё as-of окна.
15. Ручное exact decision перекрывает рекомендации; explicit_unclassified тоже.
16. Пересечение одинаковых ID в incomes и expenses не смешивает записи.
17. A/B owners, no token, wrong token, stale response across credentials.
18. Конкурентная правка между read и manual update → 409/no silent overwrite.
19. Крупная синтетическая история: bounded memory/runtime; без request-per-row.
20. Графики /analytics сохраняют исходные totals и исключают двойной учёт.
21. Полная имитация ошибочных API metadata/page/лимитов; без статусного success.
22. Ни одна рекомендация не вызывает financial mutation, side effect или AI/network provider.

## 13. Риски и альтернативы

| Подход | Преимущество | Недостаток / решение |
| --- | --- | --- |
| Только frontend-алгоритм | Быстро для демо, без нового backend API | Много истории в браузере, повторные расчёты, разные клиенты, отсутствие durable decisions; **не выбираем для production** |
| Категория = слой | Минимальный объём | Путает перевод/займ и расход; **не выбираем** |
| Backend analysis read-only | Один движок, owner-scoped history, объяснимость | Требует contract/performance/security gates; **рекомендуем первый production этап** |
| Записывать авто-класс в каждый expense/income | Быстрые GET | Массовые изменения истории и stale версии; **не выбираем** |
| Хранить manual override отдельно | Прозрачный приоритет, история не меняется | Требует новой модели, CAS и миграционного плана; **отдельное согласование** |
| AI/fuzzy matching | Может помочь неоднозначным платежам | Непрозрачные совпадения, приватность/стоимость; **не в v1** |
