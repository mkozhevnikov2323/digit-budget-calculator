# RFC: часовой пояс отчётности и точность исторических сумм

**Статус: предложение для архитектурного и продуктового ревью. Решения не утверждены.**

База frontend: `eb48c5a89a24e73b26472d62a2f89fc9ab66d511`.
Проверенный backend: `b6cafc9559608ec0592b64bcd11bc10eb17dab8a`.
Анализ выполнен чтением исходников. Работающий API, MongoDB, учётные записи и
реальная история не использовались. Все примеры ниже синтетические.

Этот PR добавляет только данный документ. Он не меняет текущую политику,
не утверждает новую и не разрешает миграцию. Для окончательного выбора и каждого
будущего изменения поведения необходимо явное согласование владельца продукта.

## 1. Предлагаемые решения

1. Для первой версии рекомендовать **постоянную отчётность в UTC (T-A)**:
   она сохраняет уже реализованную аналитику и воспроизводимость её интервалов.
   Это рекомендация по совместимости, а не вывод о предпочтениях пользователей.
   До явного одобрения UTC остаётся временным соглашением, как написано в UI.
2. Сохранить **строгий отказ от расчёта при несовместимой сумме (M-A)** и отдельно
   предложить **диагностику только для чтения (M-B)**. Диагностика объясняет причину
   и помогает владельцу найти запись, но не выдаёт частичные суммы за полные.
3. **Коррекция владельцем (M-C)** — возможная следующая функция с отдельным
   согласованием записи, аудита и конкурентного доступа. Автоматическое округление,
   массовое исправление истории и перенос дат в план первой версии не входят.

T-B/T-C остаются полноценными альтернативами. Денежные M-A/M-B/M-C могут быть
последовательными слоями, а не взаимоисключающими режимами: даже при диагностике
и коррекции итог остаётся недоступным, пока исходные данные несовместимы.

## 2. Что подтверждено исходниками

### 2.1. Даты: путь от формы до отчёта

| Участок | Подтверждённое поведение | Следствие |
| --- | --- | --- |
| Выбор даты | `DateField` — `type="date"`, значение `YYYY-MM-DD`, без IANA-зоны и времени [F1] | Календарная дата сама по себе не содержит ни смещения, ни исходного часового пояса |
| Создание дохода/расхода | `getTodayDateString()` берёт `new Date().toISOString().slice(0, 10)`; формы отправляют выбранную дату, после успеха сохраняют её в форме [F1, F2] | Значение «сегодня» по умолчанию — UTC-дата; около полуночи она может отличаться от даты браузера |
| Backend create | Joi проверяет `date` как дату, контроллеры передают её в Mongoose; модели имеют `date: Date` [B1–B3] | Для стандартной date-only строки путь соответствует UTC-полуночи. Явное смещение определяет момент, а не новую отчётную зону |
| MongoDB | Модели используют Mongoose `Date`, не отдельную календарную дату/IANA-зону [B1] | BSON Date представляет момент с точностью до миллисекунд от epoch; исходное смещение и намерение «дата операции» отдельно не сохраняются |
| Редактирование | Формы инициализируют поле через `date.slice(0, 10)` и включают это поле в PATCH [F3] | Сохранение записи с неполуночным временем может заменить его date-only значением и UTC-полуночью, даже если дату в форме не меняли |
| Старые списки | Начальный месяц/год берутся через локальные `getMonth/getFullYear`; запросы передают `month/year` [F4] | Начальный месяц браузера не обязательно равен месяцу UTC или сервера |
| Старые GET month/year | Backend создаёт границы через `new Date(year, month - 1, 1)` и аналогичные конструкторы [B2] | Эти ветви зависят от часового пояса процесса сервера и его календарных переходов |
| Строки таблиц и CSV | `new Date(date).toLocaleDateString()` без явного `timeZone`; цветовая группировка использует `toDateString()` [F4, F5] | Представление и группировка по дням зависят от браузера; формат локали не задаёт отчётную политику |
| Аналитика | `currentSelection` использует UTC-дату; PR #6 строит UTC-интервал `[startInclusive, endExclusive)` для включительных выбранных дат [F6] | Месяц/квартал/год — календарные UTC-периоды, а не скользящие длительности; домен выбранных дат 0001–9999 |
| GET аналитики | `apiRange` передаёт ISO `startDate`, `endDate = endExclusive - 1ms`, `noPagination=true`; backend использует `$gte/$lte` раньше ветвей month/year [F7, B2] | Обе коллекции запрашиваются за одинаковые явные UTC-границы; серверный TZ не определяет эти границы |
| Валидация и динамика | Date-only — UTC-полночь; timestamp требует явной зоны и точности не выше миллисекунд. Принадлежность сравнивается по моменту, месячный ключ берётся из UTC ISO [F8] | Смещение в строке не меняет сам момент; месяцы с нулём присутствуют, дневной динамики нет |

Пункт о редактировании описывает существующий путь кода, а не доказанный случай
порчи реальных данных. `date` — дата операции; `createdAt/updatedAt` не позволяют
восстановить её первоначальный календарный смысл. Переписывать историю по
предположению «все полуночи были датами, остальные — реальными моментами» нельзя.

В ветках GET с явными датами нет зависимости от локального TZ при разборе
переданных ISO со смещением/Z. Ограничение `year >= 2020` относится к отдельному
query-параметру `year`; аналитика его не посылает [F7, B3].

Write-маршруты используют `Joi.date()`, не требуют явной зоны отдельным правилом
и не сохраняют исходную строку. Для других допустимых форматов, например datetime
без смещения, интерпретация может зависеть от Joi/JS и TZ сервера. Приведённый
выше вывод о UTC-полуночи относится к стандартному `YYYY-MM-DD` текущих форм,
а не является гарантией для всех исторических источников/произвольных клиентов.

### 2.2. Примеры расхождения календарей

- Сохранённый момент `2024-04-01T00:00:00.000Z` относится к апрелю в текущей
  аналитике. В `America/New_York` это вечер 31 марта, то есть мартовский отчёт
  при политике T-B. Перенос в март возникнет без изменения BSON Date.
- Момент `2024-03-31T23:30:00Z` в `Europe/Berlin` уже относится к 1 апреля.
  Существующая форма редактирования отображает префикс `2024-03-31` из UTC-ответа
  и при сохранении может отправить `2024-03-31`, потеряв время 23:30.
- `2025-01-02T03:59:59.999+04:00` — тот же момент, что
  `2025-01-01T23:59:59.999Z`; он включён в UTC-отчёт по 1 января.
  Следующая UTC-полночь исключена.

Зоны здесь выбраны только для иллюстрации. Ни IP, ни язык интерфейса, ни локаль,
ни часовой пояс сервера/браузера, ни местоположение владельца не считаются
разрешением выбрать отчётную зону.

### 2.3. Суммы: текущие контракты различаются

| Участок | Что делает код | Чего это не гарантирует |
| --- | --- | --- |
| Добавление дохода | `AmountField` очищает строку, заменяет запятую, проверяет положительность/минимум; `AddIncomeForm` передаёт данные формы [F2, F9] | Нет общего ограничения на два дробных знака или безопасное различение соседних копеек; TS-тип `number` не превращает строку RHF в число автоматически |
| Редактирование | Доход — текстовая санитизация и `Number(value) > 0`; расход — `type=number`, `step=0.01`, минимум и RHF-проверка [F3] | HTML step не является серверной денежной политикой; обходные клиенты и другие пути не обязаны соблюдать его |
| Пакетный расход | Отдельный `priceToKopecks` принимает 1–2 дробных знака, положительную цену, ограничивает безопасный размер пакета; каждый документ получает цену `/100` [F10] | Это локальная защита конкретного потока, а не использование PR #6 всеми формами/API |
| Backend | Joi `number().min(0)`, модели `Number`, обязательная сумма, минимум 0 [B1, B3] | Нет проверки «целые копейки», ограничения precision до двух знаков или политики PR #6; Number не сохраняет исходную десятичную запись ввода |
| Старые итоги | Месячная сводка расходов и займы складывают Number; сводка отображает `toFixed(2)`, backend balance использует `$sum` и разность [F11, B4] | Округлённый вид не доказывает точность исходной истории или равенство строгой аналитике |
| Аналитика PR #6/#7 | GET amount должен быть числом; `rublesToKopecks` проверяет кратчайшее десятичное представление, не округляет; BigInt для разбора/арифметики, результат — безопасное целое число копеек [F8, F12] | Нельзя восстановить уже потерянную Number-точность или считать допустимыми любые серверные Number |

Для аналитики допустимы `0`, `0.01`, `0.1`, `0.2`; `0.1 + 0.2` как отдельный
сохранённый Number `0.30000000000000004` и `1.005` недопустимы. Числовое
`1.230` уже неотличимо от `1.23`: исходные нули и текст ввода потеряны.
Числовые строки в GET отклоняются, хотя низкоуровневый money-примитив также
умеет принимать строгие десятичные строки. Слишком большие/небезопасные числа,
переполнение, неверные записи и неполные ответы тоже останавливают отчёт.

**Расхождение не ограничено историей:** некоторые текущие пути ввода и API
не обеспечивают строгую precision-политику. Из исходников следует возможность
новых несовместимых сумм; частота и наличие таких записей — `UNVERIFIED`.
В этом RFC ни одна реальная запись не искалась и ни одна форма не отправлялась.

### 2.4. Займы, владение и полнота

Займы представлены обычными расходами с категорией «Выдача займа» и доходами
с источником «Возврат займа». `useLoanHistory` дополнительно связывает возврат
с получателем по `comment`, считает долг Number-арифметикой и показывает локальные
даты [F11]. В просмотренных маршрутах backend отдельного ресурса займов нет [B5].
Аналитика включает эти движения ровно один раз в основные суммы; отдельные
loan-подытоги используют точные исходные метки и не означают остаток долга [F8].
Ни смена зоны, ни диагностика precision не должны переклассифицировать займы.

GET/создание используют `req.user._id`; PATCH/DELETE ограничивают поиск `_id`
и владельцем [B2, B5]. Клиентский owner не заменяет серверную авторизацию.
`noPagination` возвращает `page=1`, `total=limit=длина массива`, включая ноль.
Аналитика принимает только полные ответы, но два GET не являются атомарным снимком;
метаданные не доказывают отсутствие согласованных пропусков на сервере.

## 3. Варианты отчётного часового пояса

| Критерий | T-A: постоянный UTC | T-B: явно выбранная пользователем IANA-зона | T-C: единая фиксированная зона приложения |
| --- | --- | --- | --- |
| «Сегодня», месяц, квартал, год | Календарь UTC независимо от устройства | Календарь выбранной зоны владельца; смена зоны меняет представление истории | Календарь одной явно утверждённой зоны для всех владельцев |
| Исторические моменты | Сохраняются без сдвига; текущие аналитические интервалы те же | Моменты сохраняются, принадлежность дням/месяцам пересчитывается | Моменты сохраняются, принадлежность пересчитывается относительно зоны приложения |
| DST | UTC не имеет DST; сутки по календарю UTC имеют 24 часа | Правила IANA для конкретной даты, включая исторические изменения; сутки могут иметь 23/25 часов | Для фиксированного IANA-идентификатора действуют его исторические правила/DST; постоянное числовое смещение — отдельный, иной выбор |
| Frontend | После одобрения убрать временный статус UTC; согласовать UTC-представление/фильтры отчётных экранов отдельными небольшими PR | Явный выбор и индикация зоны; новые валидируемые границы, месячные группы, «сегодня», форматирование и зависимости вычисленного кэша; отдельно согласовать формы | Та же корректная зональная календарная обработка, без пользовательского селектора; явное имя общей зоны и версия политики |
| Backend/API | Для аналитики не нужны изменения: явные ISO-границы уже поддержаны. Старые списки можно переводить на эти фильтры на клиенте | Для получения сырых записей достаточно существующих ISO start/end; хранение синхронизируемой настройки или будущая серверная группировка потребуют отдельного контракта | Для GET сырых записей изменений не требуется; единую настройку/версию политики нужно явно определить и согласованно доставлять клиенту |
| Риск изменения итогов | Низкий для текущей аналитики; унификация старых серверных month/year-списков всё же может поменять их периоды | Высокий на границах дат, особенно у записей UTC-полуночи; разные владельцы могут видеть разные месяцы для одного момента | Средний/высокий: границы меняются сразу у всех владельцев; одна зона может не соответствовать их намерению |
| Миграция | Для аналитики не нужна. Изменение дат форм не следует из выбора UTC | Миграция transaction.date не нужна для нового представления моментов. Постоянная настройка профиля может затронуть схему; восстановление «исходной даты» — отдельная нерешённая задача | Transaction.date не меняется; данных для автоматического переосмысления истории всё равно нет. Возможна только согласованная настройка, не миграция операций |
| Тесты будущей реализации | Стабильность текущих UTC-границ при разных TZ браузера/сервера, полночь, месяцы/годы, крайние годы | Всё из T-A плюс DST/исторические правила, оба смещения, смена зоны/сеанса, повторяющиеся и пропущенные локальные времена | Всё из T-B для утверждённой зоны, плюс одинаковый результат у пользователей с разными локалями/устройствами |
| Сложность | Низкая для аналитики; средняя для поэтапной унификации старых экранов | Высокая: календарь, выбор/жизненный цикл настройки, совместимость, воспроизводимость | Средняя: нет персональных настроек, но сложность IANA-календаря остаётся |

### 3.1. Правила, обязательные для T-B/T-C при их выборе

Это требования к будущей реализации, а не готовый алгоритм в данном PR:

- Построить начало первой календарной даты и начало следующей после последней
  **в выбранной зоне**, затем преобразовать границы в абсолютные моменты.
  Для текущего миллисекундного GET-контракта включительный конец — на 1ms меньше
  следующей границы. Нельзя прибавлять фиксированные 24 часа или подставлять
  текущее смещение ко всем историческим датам.
- Синтетические контрольные примеры `America/New_York`: 10 марта 2024,
  `05:00Z → 04:00Z` следующего дня, 23 часа; 3 ноября 2024,
  `04:00Z → 05:00Z` следующего дня, 25 часов. Оба вхождения повторяющегося
  осеннего часа должны попасть в выбранный день.
- Политику для неоднозначной полуночи, несуществующей полуночи и полностью
  пропущенной календарной даты утвердить явно. Предложение: начало существующего
  дня — его первый допустимый момент, при повторении — ранний; полностью
  отсутствующий выбранный день — понятная ошибка, не скрытый перенос даты.
- Валидация принадлежности, месячные YYYY-MM-группы и отображаемая зона должны
  использовать одну политику. Недостаточно поменять подпись или `toLocaleDateString`.
  Текущий `CalendarPeriod` и его проверки намеренно привязаны к UTC; нельзя передать
  туда поддельные зональные границы с прежними инвариантами.
- Явный IANA-идентификатор, календарный период и версия политики должны участвовать
  в вычисленных результатах/их кэшировании. Сырые GET с одинаковыми абсолютными
  границами можно переиспользовать; новый query-параметр `timeZone` нельзя просто
  отправлять существующим Joi-маршрутам без изменения публичного контракта.
- Неизвестная зона и неподдерживаемые границы дат должны давать ошибку, а не
  молчаливый fallback. Сохранить проверки безопасных границ домена 0001–9999,
  включая выход преобразованного UTC-момента за домен и исторические смещения.
- Нужен проверенный механизм IANA-преобразования. Наличие `Intl` для форматирования
  само по себе не даёт простого обратного преобразования календарной даты в момент.
  Выбор поддерживаемого средства/возможной зависимости — отдельное техническое
  согласование; RFC ничего не устанавливает и не реализует.
- Правила tzdb могут обновляться. Для воспроизводимости фиксировать в описании
  отчёта как минимум зону, версию политики и фактические UTC-границы; стратегию
  учёта версии tzdb определить до обещания неизменности исторических отчётов.

### 3.2. Неоднозначность исторических дат

Для T-B/T-C требуется второе решение: отображать **сохранённые моменты** в новой
зоне или пытаться сохранить **первоначальную гражданскую дату операции**.
Рекомендация для первого зонального представления, если оно будет одобрено:
сохранять моменты и заранее показывать, что принадлежность периодам меняется.
Нельзя одновременно обещать сохранение всех UTC-итогов и новый локальный календарь.

Код не доказывает, что полуночный timestamp был введён как date-only, и не хранит
историческую IANA-зону ввода. Поэтому восстанавливать гражданские даты автоматически
нельзя. Если продукту нужна именно business-date семантика, потребуется отдельный
RFC о происхождении дат, новом вводе и совместимой модели метаданных; перенос
всех `Date` или смена MongoDB-типа не являются частью этой дорожной карты.

Выбор отчётной зоны также не разрешает менять дату при сохранении старой формы.
Сохранение неизменённого исходного момента при редактировании и смысл новой
date-only записи требуют отдельной спецификации/регрессий перед изменением write-путей.

## 4. Варианты обработки несовместимых денежных сумм

| Критерий | M-A: строгий отказ | M-B: диагностика только для чтения | M-C: будущая коррекция владельцем |
| --- | --- | --- | --- |
| Результат отчёта | Итоги отсутствуют, есть причина ошибки; это текущий режим | Итоги также отсутствуют; показываются несовместимые записи/причины в защищённом UI | После подтверждённой коррекции можно заново рассчитать полный отчёт; до неё действует строгий отказ |
| История и точность | Ничего не меняется; доступность отчёта может быть низкой | Ничего не меняется; диагностика не устанавливает «правильную сумму» | Каждое изменение меняет финансовую историю и связанные отчёты; истинную сумму подтверждает владелец |
| Аудит | Видно, почему расчёт остановлен; текущая ошибка — первая, не полный реестр | Нужны полный статус проверки и безопасные ссылки на собственные записи; никаких сумм «по остальным» | Нужен неизменяемый след: кто/когда/почему, до/после, версия записи, подтверждение и результат |
| Владение | Используются существующие owner-scoped GET | Те же GET, защищённый экран, очистка данных сеанса; ID не даёт доступ к чужой записи | Авторизация на сервере в каждой операции, owner + ID + проверка конкурентной версии; подтверждение клиентом недостаточно |
| Публичный API | Без изменений | Возможен frontend на уже полученном полном ответе, без нового endpoint; серверная диагностика — отдельный контракт | Нельзя обещать достаточность текущего PATCH: условная запись, аудируемый результат и безопасный повтор могут требовать расширения/версии контракта |
| MongoDB | Number и документы без изменений | Схема и документы без изменений; никакого фонового сканирования БД | Необходим проект аудита/атомарности; новые поля/коллекции или индексы — только по отдельному одобрению и плану миграции |
| Сложность / риск | Низкая / низкий риск изменения данных, ограниченная доступность | Средняя / риск утечки диагностик и ошибочного заявления о полноте | Высокая / высокий финансовый риск; отложить до продуктовых и технических решений |

### 4.1. Почему молчаливое округление недопустимо

`1.005 → 1.01`, `1.005 → 1.00` или пропуск этой операции — разные финансовые
утверждения. Источник не объясняет намерение владельца. Округление каждой записи
и округление общей суммы могут давать разные результаты; выдача/возврат займа
также затрагивают записанные движения. `toFixed`, epsilon или умножение Number
на 100 не восстанавливают потерянную десятичную информацию.

Если округлять только аналитическое представление, оно незаметно расходится
со списками и сохранёнными документами. Если переписать БД, теряется возможность
проверить исходную историю без отдельного следа. Рекомендация — отказ от итога
до осознанного решения владельца, без частичных категорий/графиков и нулевых замен.

### 4.2. Границы безопасной диагностики M-B

- Использовать текущую precision-политику PR #6 и проверки типа GET из PR #7,
  не новый денежный парсер с другими правилами. Текущая валидация прекращается
  на первой ошибке; нельзя выдать её индекс за полный список проблем.
- В собственном защищённом UI можно показать тип набора, ID/ссылку, дату и
  причину несовместимости в минимально необходимом объёме. Общие сообщения,
  аналитические события, логи и отчёт агенту не должны содержать записи/суммы/токены.
- Объявлять полноту только для полностью полученного выбранного периода;
  ошибки метаданных, сети и дубликаты отделять от precision. Не обещать проверку
  всей истории по одному периоду; не запускать фоновую массовую проверку БД.
- Переполнение общего итога возможно и при допустимости каждой отдельной суммы.
  Это отдельная ошибка расчёта, а не доказательство ошибочности конкретной записи;
  диагностике нельзя произвольно назначать такую запись кандидатом на коррекцию.
- Не исключать несовместимые записи из общей суммы и не показывать частичные
  финансовые итоги под видом оценки. Разрешено число диагностик при явно
  подтверждённой полноте проверки, но не «сумма корректных операций» как итог.
- Не менять текущие ownership/cache-правила; при смене пользователя диагностика
  не должна переживать очистку сеанса. Все ссылки повторно проходят серверную проверку.

### 4.3. Требования к M-C и возможной будущей миграции

M-C требует явного ввода/подтверждения новой суммы владельцем на основании его
собственных документов. Никакой предвыбранной «исправленной» суммы и автоматической
пакетной записи. Нужно сохранить наблюдаемое исходное значение; неизвестный
первоначальный текст Number-ввода не следует выдавать за восстановленный факт.

Просмотр → предложение → сравнение до/после → явное подтверждение → условная
серверная запись с аудитом → подтверждение сохранения. Изменившаяся конкурентно
запись должна остановить процесс и потребовать нового просмотра. Потерянный ответ
не разрешает повторить финансовую запись вслепую. Свободный `comment` и `updatedAt`
не заменяют историю изменений; существующие модели её не содержат.

Способ атомарного сохранения записи и аудита ещё не выбран. Возможности транзакций
фактического MongoDB deployment не проверялись; нельзя предполагать replica set.
До утверждения схемы, совместимости, резервного копирования, проверки отката и
защиты конкурентного доступа функция записи не готова к реализации.

Переход Number → Decimal128/целые копейки не требуется для диагностики и не решает
семантику уже неподдерживаемых сумм. Такая миграция, если когда-либо понадобится,
должна отдельно описывать единицы/валюту, все клиенты, JSON-сериализацию, обратную
совместимость, аудит и восстановление. Автоматического разрушительного преобразования
этот RFC не предлагает. Исправление суммы и исправление даты нельзя объединять
в одну миграцию или одну незаметную операцию.

## 5. Поэтапный план после одобрения решений

Ни один из PR ниже не начинается автоматически. Две независимые линии T и M
не следует объединять в общий рефакторинг. Порядок внутри линии обязателен;
после продуктового решения сначала выполнить самый маленький совместимый шаг.

### T1 — зафиксировать выбранную зону отчётности

- **Объём/слои:** при T-A — статус и пояснения UTC в AnalyticsPage, документация,
  контрольные примеры. При T-B/T-C — отдельный небольшой PR спецификации
  внутреннего зонального периода/преобразования и синтетических тестов без включения
  нового поведения; затронут только аналитический календарный слой. Реализацию
  и возможное средство IANA-конверсии согласовать отдельно.
- **Тесты:** UTC-границы/независимость host TZ; для B/C — DST, крайние годы,
  неоднозначные/пропущенные даты и контрольные значения из §3.1.
- **Данные/API/БД:** ноль записей в финансовую историю; GET-контракт и BSON Date
  сохраняются, настройки профиля не добавляются этим шагом.
- **Откат/риск:** вернуть текст/неактивный адаптер предыдущей версии;
  низкий для A, средний для неактивной реализации B/C.

### T2 — согласованное представление отчётов и фильтров

- **Объём/слои:** после T1 отдельно согласовать старые read-only списки с явными
  границами выбранной политики. Для B/C сначала включить зональный период,
  месячную группировку, подписи и зависимости memo/cache аналитики; унификацию
  старых списков вынести следующим маленьким PR. Не менять формы записи в этом шаге.
- **Тесты:** одинаковое множество записей в аналитике/списках за одинаковые
  абсолютные границы, все страницы, переключение зоны/периода без stale totals,
  доходы и расходы на границах, нулевые месяцы и займы.
- **Данные/API/БД:** использовать существующие startDate/endDate GET; никаких
  изменений сохранённых дат/сумм. Для B способ явного выбора и хранения зоны
  сначала утверждается отдельно: сохранение в профиле может потребовать API/схему
  и не считается разрешённым данным планом. Отсутствие выбора не маскируется locale-fallback.
- **Откат/риск:** вернуть предыдущую отчётную политику без обратной миграции;
  сохранить обозначение версии и UTC-границ ранее просмотренного отчёта.
  Средний для A (старые списки), высокий для включения B/C (исторические итоги).

### T3 — отдельное решение о date-only вводе и редактировании

- **Объём/слои:** после согласования смысла даты — точечные изменения DateField,
  date helpers и create/edit-форм. Первый кандидат — сохранение исходного момента
  при редактировании без изменения даты; изменение самой даты требует отдельного
  явно описанного правила. Не выводить это разрешение только из выбора зоны отчёта.
- **Тесты:** редактирование неполуночной записи без потери времени, явная смена
  даты, DST по утверждённой политике, неуспешная/неопределённая запись без повторного сохранения.
- **Данные/API/БД:** только отдельные подтверждённые действия владельца; никакой
  массовой правки истории. Использование существующего необязательного `date` PATCH
  может сохранить контракт; новая business-date/provenance модель требует отдельного RFC.
- **Откат/риск:** откат кода не отменяет уже подтверждённые изменения документов;
  обратное изменение — отдельное действие владельца. Риск высокий, потому что это write-путь.

### M1 — диагностика несовместимых сумм только для чтения

- **Объём/слои:** отдельный сканер диагностик на money-policy PR #6, интеграция
  существующего analytics hook и защищённого UI, без дублирования расчёта итогов.
- **Тесты:** обе коллекции, несколько precision-ошибок, unsafe/overflow как отдельные
  причины, неполный ответ, отсутствующие/повторные ID, выход/смена пользователя,
  отсутствие мутаций, логов с данными и частичных итогов.
- **Данные/API/БД:** существующие GET и уже полученные ответы, новые endpoint,
  схемы, индексы и записи не нужны. Сохраняется строгий отказ M-A.
- **Откат/риск:** убрать диагностический UI, оставив текущую ошибку без записи
  в данные; риск средний из-за приватности и требований к полноте диагностики.

### M2 — отдельно согласовать предотвращение новых несовместимых сумм

- **Объём/слои:** только после утверждения области применения денежной политики —
  проверки новых/изменённых сумм в формах и серверных write-маршрутах; общие
  контрактные примеры PR #6, без переписывания остальных отчётов/истории.
- **Тесты:** обычные копейки/ноль согласно одобренным правилам, Number/string на
  границе API, unsupported/unsafe, неизменённая неподдерживаемая сумма при редактировании
  другого поля, отказ записи без ложного успеха, совместимость старых клиентов.
- **Данные/API/БД:** схема Number и существующие значения сохраняются. Более
  строгая серверная валидация — изменение допустимого публичного ввода даже при
  прежней форме JSON: нужны явное одобрение, описание ошибок и план совместимости.
  Не считать разницу UI (>0) и API/аналитики (>=0) автоматически решённой.
- **Откат/риск:** откат проверки с сохранением строгой аналитики/диагностики;
  история не меняется, но снова могут поступать несовместимые суммы. Риск средний.

### M3 — опциональная коррекция владельцем после отдельного проекта аудита

- **Объём/слои:** сначала согласовать owner-scoped условную запись, аудит,
  безопасный повтор, резервное копирование и восстановление; затем отдельно
  реализовывать просмотр/подтверждение в UI и минимальный серверный write-путь.
- **Тесты:** чужой owner/ID, конкурентная версия, атомарность аудита и изменения,
  потерянный ответ/повтор, отмена до записи, неизменность даты и остальных полей,
  перерасчёт всех зависимых отчётов/займов после подтверждения.
- **Данные/API/БД:** намеренно меняются только выбранные владельцем суммы;
  возможны отдельные API и схема аудита. Точный контракт и миграция ещё не утверждены;
  существующий PATCH не даёт всех перечисленных гарантий сам по себе.
- **Откат/риск:** отключить возможность коррекции; подтверждённые записи не стирать.
  Восстановление — согласованная компенсирующая операция с аудитом и проверкой
  актуальной версии, не автоматический rollback истории. Риск высокий; этот шаг отложен.
