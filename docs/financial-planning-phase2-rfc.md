# RFC Phase 2: финансовые слои, обязательства, резервы и цели

**Статус: проект для архитектурного и продуктового ревью. Ничего не утверждено.**

База frontend: `9aebfd8c3309a37c672a39390233f630d29215b2`.
Backend исследован чтением исходников на `b6cafc9559608ec0592b64bcd11bc10eb17dab8a`.
Единственное изменение этого PR — данный документ. Работающий API, MongoDB,
реальные записи и учётные данные не использовались; все примеры синтетические.

Обозначения: **ФАКТ** — проверенное устройство текущего кода; **ПРЕДЛОЖЕНИЕ** —
кандидат продуктового поведения; **РЕКОМЕНДАЦИЯ** — предпочтительный архитектурный
вариант; **APPROVAL** — отдельное явное решение владельца. Принятие RFC не даёт
разрешения на новые записи, CRUD, API, схемы, индексы, миграции или внедрение.

## 1. Цель и границы

Спроектировать отдельный аналитический и плановый слой поверх записанной истории.
Первый будущий PR Phase 2 содержит только чистые контракты и unit-тесты, не меняет
текущие отчёты и не переклассифицирует историю. Категория описывает назначение
операции, финансовый слой — её роль в плане владельца. Одно не заменяет другое.

Рекомендуется комбинация явных категорийных подсказок и подтверждённых назначений
отдельным операциям, сначала без хранения. Виртуальное распределение, прогноз
платежа и фактический расход — разные сущности. Ни одна из них не доказывает
наличие денег на банковском счёте. Планирование не создаёт фиктивные Income/Expense.

Строгие копейки PR #6 и полные проверенные данные PR #7 остаются основанием.
UTC остаётся **временным соглашением**: предыдущий reporting-policy RFC содержит
рекомендации, а не утверждённую политику. Эта работа не выбирает другую зону,
не округляет историю и не меняет даты операций.

Позже потребуется небольшой адаптер проверенных записей из существующего RTK Query-кэша, без повторного получения/парсинга денег |
| Займы — расходы «Выдача займа» и доходы «Возврат займа»; loan history связывает возврат с recipient через comment [S8] | Нет отдельного долгового контракта или надёжного типа transfer/refund. Аналитические loan-подытоги основаны на точных метках, не подтверждают экономическую природу любой записи |
| Raw totals включают займы один раз; динамика только месячная; два GET не являются атомарным снимком [S6–S8] | Phase 2 не меняет эти определения. Плановые суммы и резервы не добавляются в raw totals |

Одиночный текущий пользователь — предположение о режиме использования, не
разрешение убрать owner. Система уже имеет серверное разграничение по владельцу.
Пользовательская учётная запись и будущий банковский/финансовый счёт — разные понятия.
Масштаб истории, наличие банковских средств, исходные намерения и реальные
проблемные записи **UNVERIFIED**; из репозитория их установить нельзя.

## 3. Термины и логические связи — ПРЕДЛОЖЕНИЕ

Это модель предметной области, **не выбранная MongoDB-схема и не описание новых API**.
Все будущие денежные поля — RUB в безопасных целых копейках, если отдельно не
утверждена мультивалютность. Доли — немонетарные отношения; они не меняют суммы.

| Концепт | Смысл и связь |
| --- | --- |
| RecordedOperation | Существующий Income/Expense; ссылка включает вид коллекции и `_id`, поскольку одинаковые ID между коллекциями допустимы |
| LayerDefinition | Один из пяти стабильных концептуальных кодов + название + версия таксономии; не категория и не банковский счёт |
| EconomicRole | Отдельно подтверждённая природа: обычный расход/поступление, выдача/возврат займа, возврат покупки, внутренний перевод, движение капитала либо unknown |
| ClassificationRule | Явно заданная владельцем подсказка по выбранному признаку, версия, область применения; имя категории не задаёт правило само |
| ClassificationAssignment | Подтверждение владельцем для конкретной операции либо явное «оставить неклассифицированной», ссылка на версию правила/ручное решение и исходную версию операции |
| ObligationTemplate | Описание повторяемого обязательства, например ежегодного страхования; само по себе не платёж |
| ObligationOccurrence | Конкретный ожидаемый платёж со своей датой, суммой/оценкой и версией; шаблон может иметь много occurrence |
| CostEstimate | Оценка суммы с датой/основанием/статусом; замена оценки не переписывает фактическую операцию |
| AllocationPlan | Предложенный график виртуального распределения по календарным датам; не банковское движение |
| ReservationEntry | Подтверждённое владельцем виртуальное назначение, высвобождение или потребление назначенной суммы; не Income/Expense |
| PaymentLink | Подтверждённая связь части уже существующего Expense с конкретным occurrence; не создаёт ещё один расход |
| Goal / ReserveTarget | Цель/резерв с назначением, целевой суммой, необязательным сроком и версией; не актив и не подтверждение наличия денег |
| ReportedContribution | Сообщённый владельцем взнос/вывод в рамках цели; уровень доказательства явно указан, без поддельной проводки дохода/расхода |
| FundingEvidence | Будущее независимое подтверждение средств/движения по полноценному account ledger; сейчас отсутствует |

Одна фактическая расходная операция получает максимум один основной слой в
простой версии; разделение одного Expense на несколько слоёв отложено.
Её роль движения и источник оплаты — другие измерения. Например, страхование,
оплаченное из чрезвычайного резерва, может остаться расходом слоя 2: источник
денег не превращает его автоматически в расход слоя 3. Одна цель может иметь
несколько планов по версиям, но в сценарии активна только одна выбранная версия.

## 4. Пять рабочих финансовых слоёв — требуется APPROVAL

Ниже примеры, а не правила распознавания названий или рекомендации по инвестициям.

| Слой / назначение | Примеры и фактический расход | План/резерв | Что даёт история и чего не хватает | Двойной счёт |
| --- | --- | --- | --- | --- |
| 1. Повседневные расходы: регулярное потребление | Продукты, проезд, бытовые услуги; фактом является уже записанный Expense, после подтверждения его роли и слоя | Плановый лимит потребления не создаёт Expense | Можно получить суммы/число подтверждённых расходов по месяцам. Нужны классификация и отдельный бюджет для сравнения с планом | Нельзя сложить лимит и фактические покупки как два расхода |
| 2. Нерегулярные обязательства: подготовка к редким/неравномерным платежам | Страхование раз в год, ТО автомобиля, налоги, периодическая подписка, медицинский счёт, замена техники. Факт — записанный платёж, не обещание | Оценённое обязательство, occurrence и виртуальные месячные назначения | История даёт подтверждённые прошлые траты; не доказывает следующий срок, повторение или цену. Нужны явные даты, оценки, связи платежей и резерва | Назначение в резерв и платёж не суммируются как расходы; шаблон и occurrence не считаются дважды |
| 3. Чрезвычайный резерв: устойчивость к неожиданным событиям | Непредвиденное лечение/срочный ремонт могут быть отдельно подтверждённым расходом слоя 3. Перевод на свой резервный счёт сам по себе не потребление | Целевой запас и виртуальное назначение; например выбранное число месяцев необходимого бюджета | История даёт только явно классифицированные чрезвычайные расходы. Наличие/размер фонда и достаточность не выводятся без цели, основания бюджета и подтверждения средств | Нельзя считать резерв расходом, а затем повторно считать оплату из него; один запас не обеспечивает сразу несколько целей |
| 4. Крупные цели: отдельные значимые покупки | Планируемый автомобиль, ремонт, крупная техника; расход возникает при реальной записи оплаты, не при постановке цели | Целевая сумма/срок и график накопления; взносы — отдельная плановая информация | Можно связать уже записанные покупки с подтверждённой целью. Для прогресса нужны явная цель, история назначений/взносов и уровень доказательства | Покупка не добавляется к сумме накоплений как ещё одна стоимость цели; взнос и резерв могут описывать одни деньги |
| 5. Долгосрочный капитал: длительный горизонт сохранения/роста средств | Приобретение актива, если занесено как Expense, остаётся в raw totals, но не становится обычным потреблением. Комиссия может быть отдельным обычным расходом | Цель взносов и горизонт, не прогноз доходности | История показывает только записанные движения. Стоимость капитала/доходность требуют позиций, котировок, комиссий, обязательств, дат оценки и account ledger | Покупка актива, перевод своих денег и рост рыночной стоимости — разные вещи; их нельзя складывать как расходы или капитал |

Границы слоёв 2/3/4 требуют решения владельца: например плановая замена техники
и чрезвычайная поломка отличаются намерением, а не одной категорией «Техника».
Не всякому движению нужен слой обычных расходов. Для подтверждённых займов,
переводов и возвратов должен существовать явный отдельный режим, а не принудительный
выбор из пяти слоёв. Неразобранные записи остаются неклассифицированными.

## 5. Классификация как независимое измерение

### 5.1. Сравнение вариантов

| Критерий | A. Явное соответствие категории слою | B. Назначение каждой операции | C. Категорийные подсказки + подтверждённые назначения/исключения |
| --- | --- | --- | --- |
| Работа владельца | Вручную выбирает категорию/строковую метку, слой и область правила; предварительно видит затронутые записи | Просматривает конкретную операцию, назначает слой/роль либо оставляет unclassified | Задаёт подсказку, просматривает предложенные назначения и подтверждает; может явно отменить подсказку для операции |
| Владение / system vs custom | Правило всегда принадлежит владельцу, даже для общей системной категории; общий словарь не меняется | Назначение имеет того же owner, что и операция; проверка на сервере при будущем хранении | Оба условия; чужое правило не влияет на мой отчёт. Никаких глобальных слоёв на системной категории |
| Rename/delete | Нужны версия/снимок метки; нельзя автоматически перекинуть старые операции на новый ID по имени | Ссылка на операцию переживает изменение словаря, но изменение самой операции требует повторной проверки | Новая версия подсказки; принятые назначения не меняются. Отсутствующий словарь не стирает историю решения |
| История и версии | Применение «последнего правила ко всей истории» меняет старые отчёты; нужны явная область, версия и подтверждение пересчёта | Сохраняется версия решения и проверяемый снимок фактов операции | Подтверждение хранит версию подсказки/таксономии и факты операции; новый default сам ничего не переписывает |
| Согласованность | Одна категория часто содержит разные роли; коллизии имён особенно опасны | Лучше объяснимость, больше ручной работы; конфликты версий блокируют результат | Приоритет явного решения, unclassified и подсказки; неоднозначность не разрешается случайным порядком |
| Сложность / миграция | Низкая для preview; средняя для честной истории. Позже потребуется учёт исключений | Средняя; будущий слой правил можно добавить, не меняя транзакции | Средняя/выше, но можно вводить по частям: контракты → preview → review → отдельное хранение. Перенос исходных Expense/Income не нужен |

**РЕКОМЕНДАЦИЯ: C, с ручным подтверждением назначения, а не автоматическим
применением подсказок к истории.** Для небольшого объёма одного владельца сначала
достаточно временного preview; owner и ревизии нужны сразу, не «после multi-user».

### 5.2. Правила разрешения и сохранения смысла истории

1. Ключ операции — `(dataset, _id)` в области текущего владельца. У назначения
   есть статус `proposed / approved / explicit_unclassified`, версия, основной
   слой или отсутствие слоя, economicRole, источник решения, подтверждающий и
   дата подтверждения. Это логический контракт, не поля MongoDB в этом PR.
2. Актуальное подтверждённое ручное решение имеет приоритет; явное
   `explicit_unclassified` не заменяется default. Без подтверждения результат
   остаётся unclassified; подсказка видна отдельно. Два противоречащих актуальных
   назначения — ошибка согласованности, а не «берём последнее по времени».
3. В исходной операции только строка категории. Текущий selector может означать
   только явно подтверждённую **исходную строковую метку**, а не доказанный ID
   системной/пользовательской категории. При совпадении имён UI обязан объяснить
   область. Пока владелец её не подтвердил, не предлагать результат как установленный.
4. Не использовать fuzzy matching, название слоя, регистр, AI или догадку по
   recipient/comment. `constructor`, `__proto__`, Unicode и отсутствие категории
   обрабатываются как данные. Missing и буквальное «Без категории» различимы в
   provenance, даже если Phase 1 группирует их вместе. Правила нормализации должны
   быть явно частью версии, а не случайным поведением UI.
5. Подтверждение относится к перечисленным операциям и их фактам: сумма, момент,
   исходная метка/роль и доступная версия. Правило подтверждения будущих записей
   по умолчанию **не включено**. Новые записи сначала получают подсказку;
   расширение области на прошлое/будущее требует отдельного явного действия.
6. Изменение суммы/даты/категории/source делает относящееся к этим фактам решение
   устаревшим; не пересчитывает историю молча. Нужен новый review, а старый снимок
   отчёта указывает прежние версии. `updatedAt`/fingerprint полезны для preview,
   но сами не заменяют серверную условную запись и проверку owner.
7. Будущее удаление категории — прекращение применения подсказки, не каскадная
   очистка назначений. Будущее удаление операции — ссылка становится недействительной
   для текущего отчёта, сохраняется объяснение прежнего решения; никаких фиктивных
   расходов для её «восстановления». Поведение архива/retention ещё нужно согласовать.

При будущей интеграции нужны проверенные индивидуальные записи и исходные метки
из тех же полных RTK Query-ответов. Небольшой адаптер связывает их с проверенными
`id/timestamp/kopecks`, сохраняя денежную/календарную валидацию Phase 1. Он не должен
извлекать операции из агрегатов, дублировать денежный парсер, считать currentData
другого периода актуальными или повторно обходить backend. Первый PR этого не делает.

### 5.3. Займы, возвраты и переводы

Известные Phase 1 метки займов показываются как существующие label-based движения,
но не становятся автоматическим правилом нового слоя. Для нормализованного показателя
нужна подтверждённая economicRole. `loan_issuance`, `loan_repayment`, `transfer`,
`refund` и `capital_movement` отдельно от обычного потребления; unknown не равен ordinary.

Выдача и возврат займа остаются в raw totals. Возврат покупки пока показывается
отдельным подтверждённым поступлением; автоматически вычитать его из расходов
другого периода нельзя. Для будущего net-spending понадобятся связь с исходным
Expense, частичные возвраты, межпериодное правило и ограничения сумм. Внутренний
перевод требует доказательства обоих концов и охвата счетов; сегодня такого ledger
нет. Источник «Перевод» или комментарий не являются достаточным доказательством.

## 6. Нерегулярные обязательства и план резервирования

### 6.1. Состояния и входы

Исторический Expense — факт записанной оплаты. План будущего платежа — occurrence.
Обязательство может быть договорным или добровольной оценкой; надпись «обязано»
не выводится из прошлой частоты. Повторение задаётся явно шаблоном: например
ежегодное страхование, периодический налог/подписка. ТО, лечение и бытовая покупка
могут иметь только ручную оценку без известного повторения.

Occurrence содержит логически: owner, стабильный идентификатор, необязательный
templateRef, слой, дату срока, ожидаемую сумму `C`, статус `estimate/confirmed`,
дату/основание оценки, версию и состояние active/cancelled. Конкретные платежи
подтверждаются PaymentLink к существующим расходам, а не переключателем «оплачено»
без доказательства. До такого linking можно показывать только самоотчёт владельца.

План рассчитывается для явно переданной `asOfDate` A после завершения этого дня,
конкретного occurrence и сценария. Обязательные входы: `C`, срок, известная
оплаченная часть `P`, остаток виртуального назначения `R`, правило дат взносов,
ревизии данных. `P=0`/`R=0` допустимы только как явно известные нули;
отсутствие данных не превращается в ноль. История не позволяет вывести R из I−E.

### 6.2. Точное правило — ПРЕДЛОЖЕНИЕ для первой реализации

Все денежные входы — неотрицательные безопасные целые копейки. Никаких дробных
копеек на входе, float-rounding или изменения PR #6. Для сумм/разностей используются
его операции, для будущего целочисленного деления/остатка — BigInt с проверкой
выходного диапазона. Новые чистые плановые функции будут отдельными модулями.

1. `outstanding = max(C − P, 0)` — остаток относительно ожидаемой стоимости.
   `P > C` отмечается как превышение оценки, не автоматически ошибочный платёж.
2. `D = max(outstanding − R, 0)` — ещё не покрытая **плановыми назначениями** сумма.
   Излишек `R − outstanding`, если положителен, показывается отдельно;
   его нельзя автоматически назначить другой цели или назвать свободными деньгами.
3. Взносы по умолчанию планируются на 1-е число месяца. Выбираются даты S,
   удовлетворяющие **A < S < dueDate**. Взнос в день самого платежа не предполагается
   доступным до него. Это продуктовая рекомендация, не установленная привычка дохода.
4. `N` — число таких дат. При `D=0` дополнительных назначений не нужно; это не
   означает «оплачено». При `D>0, N=0` результат — дефицит D без доступных дат,
   а не нулевой взнос/деление на ноль. Прошедший срок и неоплаченный остаток
   обозначаются отдельно, даже если он виртуально покрыт резервом.
5. При `N>0`: `q = D div N`, `r = D mod N`. Первые r дат в хронологическом
   порядке получают `q+1` копеек, остальные q. Сумма графика **ровно D**.
   Показывается график и ближайшая плановая сумма, не вечная округлённая ставка.

Статусы оплаты (нет/частично/записанная оплата покрывает оценку), просрочки и
планового покрытия независимы. Если известна только оценка C, итог — оценочный
план, не гарантированный будущий расход. Общая месячная потребность — сумма
уникальных активных occurrence одного сценария, не сумма всех версий/шаблонов.
Не добавлять к ней ещё раз уже вычтенные R и P или записанные назначения.

Даты строятся календарными функциями PR #6, UTC пока provisional. День взноса
29–31, если будет разрешён, требует утверждённого правила; кандидат — ограничение
последним числом месяца, без JS-rollover в следующий месяц. Для ежегодного 29 февраля
нужно выбрать 28 февраля / 1 марта / только високосный год; до выбора нет скрытого
правила. Повторение создаёт только прогноз occurrence с уникальной парой
«шаблон + плановая дата», не автоматические реальные записи или scheduler.

Неизвестная цена/дата, ошибочный диапазон, отрицательный остаток резерва, дубликат
связи или переполнение дают явную ошибку/«недостаточно данных». При C=0 плановая
потребность равна нулю, но факт оплаты не выдумывается. При переносе срока/новой оценке нужна
новая версия плана; уже записанные оплаты не редактируются. Для нескольких
обязательств нет автоматической оптимизации «по доступным деньгам»: таких денег
модель не знает. Приоритеты и допустимый бюджет задаёт владелец отдельно.

### 6.3. Пример: годовое страхование и остаток копейки

Синтетически: A = `2026-02-15`, срок `2026-06-15`,
`C=1 200 001` коп. (12 000,01 ₽), `P=0`, `R=200 000` коп. (2 000,00 ₽).
Даты взносов — 1 марта, 1 апреля, 1 мая, 1 июня; N=4.

`D=1 000 001`, `q=250 000`, `r=1`:

| Плановая дата | Копейки | Отображение |
| --- | ---: | ---: |
| 2026-03-01 | 250 001 | 2 500,01 ₽ |
| 2026-04-01 | 250 000 | 2 500,00 ₽ |
| 2026-05-01 | 250 000 | 2 500,00 ₽ |
| 2026-06-01 | 250 000 | 2 500,00 ₽ |
| Всего | 1 000 001 | 10 000,01 ₽ |

Если до следующего годового платежа доступны ровно 12 дат и R=P=0, то для
того же C получится первый взнос `100 001` коп. и ещё 11 по `100 000` коп.
Деление на 12 допустимо именно из-за 12 доступных дат, не из-за слова «годовой».

### 6.4. Пример: резервирование и платёж не два расхода

После назначения 1 марта `250 001` коп. виртуальный R стал `450 001`.
Потом владелец связал существующий Expense `300 001` коп. с этим occurrence и
явно указал потребление той же части виртуального резерва:

- `P=300 001`, остаток R=`450 001−300 001=150 000`;
- outstanding=`1 200 001−300 001=900 000`, D=`900 000−150 000=750 000`;
- на A=`2026-03-15` остаются 3 даты по `250 000` коп.

До платежа D также был `1 200 001−450 001=750 000`: одна и та же часть не
вычтена повторно. В raw expenses учитывается только исходный Expense `300 001`;
ни назначение `250 001`, ни потребление резерва не создают Expense/Income.

Резерв не всегда оплачивает платёж: связь оплаты и потребление R подтверждаются
раздельно, не выводятся автоматически из совпадения суммы. Если платёж был из
других средств, R может остаться неизменным, а излишек плана показывается отдельно.
Если он был из этого резерва, обе связанные записи виртуального состояния должны
быть согласованы в одном утверждённом событии плана; атомарность будущего хранения
требует отдельного проекта, не двух ненадёжных независимых запросов.

Сумма частей одного Expense по **всем** PaymentLink не должна превышать его
проверенную сумму; одна часть не оплачивает два occurrence. Связь уникальна,
owner у обоих объектов одинаковый. Платёж без достаточного виртуального R всё
равно может существовать как факт, но нельзя списать R ниже нуля. Последующее
изменение/удаление Expense делает связь требующей review, не пересчитывает её молча.

### 6.5. Пример: срок уже недостижим графиком

A=`2026-06-01`, срок=`2026-06-01`, `C=100 000`, `P=20 000`, `R=10 000` коп.
N=0, D=`70 000` коп. Результат — дефицит 700,00 ₽ и отсутствие будущих дат,
а не «ежемесячно 0 ₽». Если срок прошёл, отдельно виден неоплаченный остаток.
Если дата или стоимость медицинской помощи неизвестна, месячный взнос вообще
не вычисляется: требуется оценка/сценарий владельца, не догадка из категории.

## 7. Чрезвычайный фонд, крупные цели и капитал

Цель имеет целевую сумму T>0, назначение/слой, необязательный срок, версию и
владельца. Без срока можно показать цель и подтверждённый уровень плановых сведений,
но нельзя вычислить сроковый месячный взнос. Для чрезвычайного фонда кандидат
цели — `T = B × m`, где B — явно утверждённый положительный месячный необходимый бюджет в
копейках, m — выбранное положительное целое число месяцев; произведение проверяется
на overflow. Ни B, ни m не выбираются автоматически из всех raw expenses.

| Представление | Что означает прогресс | Достоинства / ограничения |
| --- | --- | --- |
| Только цель | Цель известна, фактическое финансирование неизвестно | Минимум предположений; отсутствие данных не 0% и не «профинансировано» |
| Виртуальные назначения | Остаток назначений R, отношение R/T, подпись «назначено по плану» | Полезно для бюджетирования, но нет доказательства денег; единая виртуальная книга нужна, чтобы не назначить один остаток нескольким целям |
| Заявленные владельцем взносы/выводы | Известный начальный заявленный остаток + заявленные взносы − выводы; отношение к T, подпись «заявлено владельцем» | Более содержательный самоотчёт, но не банковское подтверждение. Отрицательный/неизвестный остаток — ошибка/неизвестно, а не автоматически ноль |
| Проверенное финансирование | Остатки/связанные движения по полному account ledger с датой сверки и покрытием счетов | Сейчас невозможно вывести. Требует отдельного account/transfer дизайна и согласования, не добавления фиктивного дохода/расхода |

Виртуальные назначения и заявленные взносы могут описывать те же деньги:
их нельзя складывать для одного прогресса. При начальном неизвестном остатке
чистый поток взносов сам по себе не является балансом. Известный остаток и T
задают отношение без округления денег; процент округляется только для отображения.
Превышение 100% показывается явно, не теряется через обрезание суммы.

Контроль двойного назначения требует явно заданного виртуального пула V —
допустимого планового лимита владельца, **не подтверждённого остатка банка**.
В одном согласованном сценарии сумма остатков R всех конвертов плюс неназначенная
часть равна V. Назначение уменьшает неназначенную часть, высвобождение возвращает
её, перенос между целями сохраняет общую сумму; потребление уменьшает R и V
одновременно. Изменение самого лимита V — отдельное явное плановое событие,
не новый Income. Без известного V можно рассматривать отдельные сценарии, но
нельзя утверждать их совместную обеспеченность или отсутствие перекрытия средств.
Даже согласованная виртуальная книга подтверждает только внутреннюю непротиворечивость
назначений, не реальную ликвидность и не происхождение денег.

Синтетически B=`5 000 000` коп. (50 000 ₽), m=3: T=`15 000 000` коп. (150 000 ₽).
R=`4 000 000` коп. даёт 26,67% **виртуально назначено**. При явно известном нулевом
начальном самоотчёте, взносах `2 500 000` и выводах `500 000` коп. получается
`2 000 000` коп., 13,33% **заявленного остатка**. Складывать эти 26,67% и 13,33%
нельзя. Проверенные средства на счетах остаются неизвестными, не 0 ₽.

Для крупной покупки платёж и достижение плановой цели — разные статусы.
Покупка может быть оплачена в кредит, поэтому достижение T само не доказывает
завершение оплаты, а факт оплаты не доказывает накопление из собственных средств.
Для долгосрочного капитала взносы, стоимость активов и доходность — отдельные
показатели; без позиций, рыночной оценки и обязательств net worth не рассчитывается.

## 8. Предлагаемые показатели и блокировки

Новые нормализованные показатели не заменяют Phase 1. Для всех history-derived
сумм применяются полная валидация обоих наборов, точные копейки, тот же период и
отсутствие stale данных. Ошибка precision/даты/ID/метаданных/overflow или refetch
блокирует результат, а не превращает его в ноль. Отсутствие классификации —
отдельное видимое состояние, не permission для догадок. «Обычные расходы целиком»
недоступны, пока остаются неизвестные роли/нужные назначения.

| Показатель / тип | Источник и точная формула | Займы, возвраты, переводы / достоверность |
| --- | --- | --- |
| Записанные поступления I — факт записи | `sumKopecks` всех проверенных Income периода | Всё записанное включено, в том числе займы/возвраты/переводы, если они внесены как Income. Уже доступно; не заработанный доход и не остаток счёта |
| Записанные расходы E и I−E — факт записи | Все проверенные Expense; `subtractKopecks(I,E)` | Всё записанное включено ровно один раз. Уже доступно; разность не доступные деньги, богатство или сбережения |
| Записанные движения займов — факт по метке | Существующие `loans.issuedKopecks` / `returnedKopecks` | Достоверно как суммы точных меток Phase 1, не как юридический остаток долга; не добавлять их повторно к I/E |
| Обычные записанные расходы O — классифицированный факт | Сумма Expense с подтверждённой ordinary-spending ролью и утверждённым слоем | Займы, возвратные/внутренние переводы и capital principal отдельно. Требуются назначения/полнота ролей; одних категорий сейчас недостаточно. Возвраты не вычитаются автоматически |
| Нерегулярные записанные расходы — классифицированный факт | Та же обычная расходная выборка, слой 2 | Планы/резервы исключены; нужны явные назначения, не частота встречаемости категории |
| Неклассифицированные операции U — факт отсутствия решения | Отдельно по Income/Expense: сумма и число операций без актуальной подтверждённой роли либо требуемого слоя, кроме явно подтверждённых исключённых движений | Не объединять доходы и расходы в один положительный денежный total; unknown не исключать из raw. Требуется полный снимок состояния назначений; при его загрузке U неизвестно, не ноль |
| Распределение E по слоям — классифицированный факт | Каждая Expense ровно в одном из пяти слоёв ordinary-spending, unclassified или отдельном confirmed-nonspending bucket; сумма корзин = E | Подтверждённое движение капитала не включается в обычные траты слоя 5. Статус роли имеет приоритет над слоем; conflicting assignments блокируют распределение |
| Месячная плановая потребность — план/оценка | Сумма сумм графиков §6 для дат выбранного месяца, по уникальным активным occurrence и одной версии сценария | Фактические оплаты P и назначения R уже учтены в D. Займы/переводы не притворяются доходным источником покрытия. Не хватает C/срока/R — нет полного общего итога, не сумма только известных планов |
| Остаток виртуальных назначений — план | Явно известный начальный виртуальный остаток + назначения − высвобождения − потребление, на as-of | Не E, не I, не банк-баланс. Нужны целостная виртуальная книга и отдельное подтверждение потребления; нельзя автоматически пополнить возвратом займа/покупки |
| Подтверждённые возвраты покупок — классифицированный факт | Сумма Income с одобренной refund-ролью и необходимой связью | Включены в I. Net-spending с вычитанием не предлагается до отдельной межпериодной/частичной refund-политики |
| Прогресс цели — план / самоотчёт | R/T или известный заявленный остаток/T, строго раздельно и с уровнем доказательства | Сейчас только предлагаемые данные. Фактическое финансирование и рыночная стоимость недоступны без отдельной модели |

Для будущих агрегатов планов все выбранные активные обязательства должны иметь
валидные входы. Отдельный корректный сценарий можно рассмотреть сам по себе с
названием/версией, но нельзя выдать его за итог всего бюджета. При неполноте
классификации разрешены raw totals и явно показанные корзины, не полный O.
Чистый план без ссылок на историю может вычисляться независимо от сетевой ошибки
истории; план с P/ссылками на платежи блокируется, пока они не проверены.

## 9. Альтернативы хранения — решение ещё не принято

### 1. Временные классификации только в клиенте

- **Плюсы:** без API/схем/миграции; удобно для первого preview. **Риски:** потеря
  при закрытии/перезагрузке, нет межустройственной версии или доказательства сохранения.
- **Owner/история:** только текущий сеанс владельца; очищать при logout/смене owner;
  raw history не меняется. Не использовать общий localStorage как скрытое постоянное хранилище.
- **Concurrency/API/БД:** локальный version/fingerprint и обнаружение устаревания;
  серверного CAS нет, API и MongoDB без изменений.
- **Миграция/откат:** перенос черновика в будущее хранение только после нового
  review, без silent upload; откат — убрать preview и потерять лишь явно временный черновик.

### 2. Отдельные owner-scoped документы правил/назначений

- **Плюсы:** не затрагивают формы/схемы операций, поддерживают происхождение,
  версии и исключения. **Риски:** ссылки, конфликты, удалённые операции/категории,
  согласованность версий и дополнительная авторизация.
- **Owner/история:** owner обязателен, сервер проверяет принадлежность операции
  и пользовательского словаря. Правило на системную категорию всё равно личное;
  версии/снимки решений позволяют объяснить исторический отчёт.
- **Concurrency/API/БД:** новые API и отдельные схемы только после APPROVAL;
  условная запись ожидаемой ревизии, запрет конфликтующих активных назначений,
  проверка актуальности фактов операции. Реальные индексы/атомарность ещё не выбраны.
- **Миграция/откат:** новые документы без backfill операций; прежние клиенты их
  игнорируют. Откат чтения/записи к raw аналитике, данные решений сохраняются
  согласно retention, не удаляются общей clean-up миграцией.

### 3. Необязательный layer/default на существующей категории

- **Плюсы:** простая настройка рядом со справочником. **Риски:** общая системная
  категория не должна хранить личный выбор; string Expense всё равно не является FK;
  смена поля способна переосмыслить всю историю без исключений.
- **Owner/история:** для system category понадобится личный overlay; иначе выбор
  одного пользователя затронет остальных. Без ревизий нельзя воспроизвести старый отчёт.
- **Concurrency/API/БД:** изменения category-схем и API, CAS/версионирование;
  текущий GET/POST не имеет такого контракта. Переименование не переписывает Expense.
- **Миграция/откат:** поле необязательное, старые документы unclassified;
  откат игнорирует поле, не исправляет историю. Позже overlays практически
  приводят к варианту 2. Не рекомендуется как основной формат.

### 4. Необязательная классификация на самой операции

- **Плюсы:** простой доступ к назначению вместе с транзакцией. **Риски:** смешение
  аналитического решения и финансовой записи, конфликты с edit-формами, нет истории
  через один current layer; старые клиенты могут не учитывать новые поля.
- **Owner/история:** owner исходной операции, отдельный аудит аналитических решений;
  отсутствие поля unclassified, без автоматического backfill.
- **Concurrency/API/БД:** новые поля Expense/Income и контракты мутаций/ответов;
  смена слоя не должна перезаписывать amount/date. Нужна согласованная условная запись.
- **Миграция/откат:** сохранить обратную совместимость неизвестных полей у клиентов,
  отключить интерпретацию, не массово чистить/откатывать суммы. Не рекомендуется в начале.

### 5. Отдельные planning/obligation/goal сущности

- **Плюсы:** планы отделены от фактов, есть occurrence, версия сценария и связи
  оплаты без фиктивных операций. **Риски:** повторные occurrence, конкурирующие
  назначения одного резерва, доказательность, аудит и атомарность связанного события.
- **Owner/история:** все сущности и связи одного owner; никакой ссылки на чужой
  Expense/цель. Финансовые счета — отдельная будущая модель, не поле owner.
- **Concurrency/API/БД:** потребуются отдельно одобренные схемы/API для каждого
  вида данных, ревизии, защита повторов и согласованность payment/reservation event;
  MongoDB deployment/возможности транзакций не проверены, их нельзя предполагать.
- **Миграция/откат:** добавление только новых планов с явным участием владельца,
  без превращения истории в recurring commitments. Откат отключает planning UI/записи;
  raw history остаётся, сохранённые планы/аудит не удаляются автоматически.

**РЕКОМЕНДАЦИЯ:** начать с 1; после отдельного schema/API-решения выбрать 2 для
классификации и рассматривать 5 для планирования. Это предпочтение архитектуры,
не выбор конкретной Mongoose-схемы. Approval категории mapping не распространяется
на obligations/goals/reservations. Финансовые коррекции, классификация и плановые
назначения не объединяются в один endpoint или одну операцию сохранения.

  неактивный модуль; последующее хранение требует собственного плана отката.

Проверка этого PR ограничена чтением исходников, согласованностью документа,
наличием ссылок и `git diff --check`. Jest, ESLint, build, миграции и live API-проверки
не запускаются. CI не изменяется; существующий workflow может стартовать автоматически
при открытии PR. Реальные средства, настройки deployment, объём истории и успешность
ручной приёмки не проверены. Согласование модели данных ещё не выполнено.
